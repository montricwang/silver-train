# ADR-002: v1 使用结构化知识 + Prompt 而不是 RAG

## Status
Accepted（2026-05-07）

## Context
v1 在搜韵 API 提供的基础格律数据之上，需要引入"声情分析"
的内部知识——具体来自龙榆生《词学十讲》第四讲（句度长短）
和第五讲（韵位安排）等理论框架。

业界常见做法是 RAG（向量检索召回片段），但本项目有几个特殊点：

1. 知识源特征：《词学十讲》是高度结构化的理论书，
   十讲对应十个清晰的分析维度，理论藏在例证里但骨架明确。
   不是大规模零散文本。

2. 任务性质：我们的任务是"对一首词应用固定框架做分析"，
   不是"用户提开放问题找相关段落"。前者需要完整框架，
   后者才是 RAG 的典型场景。

3. 项目阶段：v1 只覆盖格律一个维度（见 ADR-0003），
   涉及理论范围有限，结构化提炼是可行的。

## Decision
v1 不引入向量数据库或 RAG 流程。改为：

1. 人工 + AI 辅助，从龙榆生《词学十讲》第四、五讲提炼出
   结构化知识，存为 `data/knowledge/ryusl-framework.yaml`
2. 分析时将该 YAML 作为 prompt 的一部分，连同搜韵 API
   返回的客观格律数据，一起送入 LLM 做综合判断
3. 客观可计算的指标（句长分布、韵位密度等）由代码直接计算，
   不交给 LLM

## Consequences
好处：
- 任务匹配：分析任务需要的是完整框架，prompt 注入比 RAG
  召回片段更合适
- 准确性高：规则明确写在 prompt 里，输出可追溯到具体规则
- 成本低：单次 LLM 调用，不需要切片 + 向量化 + 召回链路
- 可控可调：YAML 改一行立刻生效，不用重新构建 embedding
- 可解释性强：面试时能讲清楚"为什么 LLM 这样判断"
- 留下了清晰的 v2 升级路径

代价 / 风险：
- 个人 + AI 对原文的提炼可能有偏差，需要回溯校验
- YAML 体量增长后会挤占 prompt token 预算
- 如果未来要扩到 5+ 本理论书，结构化的人工成本会变大

何时重新评估：
- v2 扩展到《词话丛编》等大规模历代词话语料（那是 RAG 的真场景）
- 结构化知识 token 量超过 context window 容量
- 出现明显的"框架无法 cover"的新分析维度

## Alternatives Considered
- A. RAG（向量检索 + 召回）
  没选：龙榆生书是结构化理论而非零散文本；分析任务需要完整
  框架而非检索片段；引入切片 + embedding + 召回链路会增加
  不确定性和工程成本，与 v1 的 sprint 节奏不符。
  保留给 v2——当扩展到历代词话大规模语料时再启用。

- B. 用其他作者（吴梅、王国维、叶嘉莹等）的书替代
  没选：龙榆生在格律领域有公认权威性，且《词学十讲》本身
  覆盖了 v1 需要的所有维度。其他书留给 v1.5+ 增补。

- C. 不引入内部知识，直接靠 LLM 通用能力
  没选：LLM 对词学的理解是泛泛常识级，无法对应到具体的
  "龙榆生声情框架"。失去项目的核心差异化。

- D. 把整本书直接塞进 system prompt
  没选：token 浪费严重，且原书的论述风格不是"规则"形式，
  LLM 难以稳定提取应用。结构化提炼是必要的中间步骤。
