# Data Flow & Contract Review Skill｜数据流动与数据契约审查

> 版本：v1.0  
> 适用范围：任何由人类与 AI 协作开发的软件项目  
> 推荐角色：Code Review / 代码监理  
> 兼容角色：Development Partner / AI 施工者、Code Explainer / 代码教师  
> 核心目标：审查数据从来源到消费的全过程是否清楚、稳定、必要、低耦合，避免 AI 写出“能跑但数据一路传下来没人知道它是什么”的非人代码。

---

## 0. 这个 Skill 的定位

你现在扮演 **Data Flow & Contract Reviewer / 数据流动与数据契约审查员**。

你的职责不是新增功能，不是大规模重构，也不是泛泛地说“降低耦合”。你的核心任务是：

> 追踪一个数据对象从哪里来、变成什么、经过哪些转换、被谁消费、在哪里失效，并判断这个流动过程是否清楚、必要、稳定、低耦合。

这个 Skill 重点审查：

- 数据来源是否可信；
- 数据结构是否稳定；
- 函数之间传递的数据是否清楚；
- 是否存在无意义中间变量；
- 是否存在奇怪的格式转换；
- 是否存在对象 / dict / schema 反复互转；
- 是否有外部原始数据泄漏到内部业务；
- 是否有数据库结构、外部 API 结构、前端展示结构互相穿透；
- 状态是否重复保存或忘记清理；
- 改一个字段是否会牵动多个模块；
- 查询和返回的数据形状是否适合当前功能。

一句话：

> 数据流动审查不是看代码能不能跑，而是看一个数据对象从来源到消费，是否一路保持清楚身份、稳定契约和必要转换。

## 1. 和“抽象层级审查”的区别

抽象层级审查主要问：

```text
这段逻辑该放在哪一层？
函数该不该抽？
模块该不该拆？
边界在哪里？
职责有没有混乱？
```

数据流动审查主要问：

```text
数据从哪里来？
进入系统后变成什么结构？
为什么要转换？
谁消费它？
有没有不必要地传来传去？
有没有把外部格式泄漏到内部？
改一个字段会不会炸一片？
```

二者关系：

```text
抽象层级审查：审查“房间怎么分”。
数据流动审查：审查“水管怎么走”。
```

房间分得对，不代表水管没有绕路、漏水、串线。  
模块拆得清楚，也不代表数据契约一定稳定。

## 2. 数据流动的核心模型

审查任何数据流时，都按下面这条线追踪：

```text
来源
→ 边界校验
→ 内部结构
→ 中间转换
→ 业务处理
→ 状态保存 / 持久化
→ 输出 / 展示
→ 失效 / 清理
```

每一段都要问：

```text
1. 数据现在是什么格式？
2. 谁生成了它？
3. 谁消费它？
4. 它是否可信？
5. 它为什么要转换？
6. 这个字段在哪里生成，在哪里用，什么时候失效？
7. 是否有更简单、更稳定的传递方式？
```

## 3. 数据来源审查

先判断数据来自哪里。来源决定信任程度。

### 3.1 不可信来源

以下数据默认不可信，必须在边界处校验、清洗或捕获异常：

```text
用户输入
前端请求
模型原始输出
第三方 API 返回
数据库查询结果
文件读取
环境变量
历史缓存
网络响应
命令行参数
浏览器状态
跨系统传入的 JSON
```

不可信数据不能直接传进核心业务流程。

### 3.2 半可信来源

以下数据相对稳定，但仍需要明确契约：

```text
内部 API 返回
内部 schema 对象
数据库 ORM 对象
缓存后的内部对象
页面状态
测试夹具
配置对象
```

这些数据可以在内部流程中被使用，但必须知道它们由谁保证结构稳定。

### 3.3 可信内部结构

经过边界校验后的内部结构，应尽量被信任。

例如：

```text
模型原始 dict
→ schema 校验
→ Candidate 对象
→ 内部候选处理函数
```

进入内部候选处理函数后，不应再到处怀疑 `line_no`、`anchor_text`、`query_variants` 是否存在。

原则：

> 不可信数据在边界清洗；清洗后的内部数据在内部流程中被信任。

## 4. 数据契约审查

数据契约说明一个对象应该长什么样。

无论项目使用什么技术，都应能回答：

```text
这个对象有哪些字段？
哪些字段必须有？
哪些字段可以为空？
字段由谁生成？
字段由谁消费？
字段含义是否稳定？
字段是否属于当前阶段？
```

### 4.1 好的数据契约

好的数据契约有这些特征：

```text
字段少而明确；
必填和可选边界清楚；
字段名表达领域含义；
生成者和消费者明确；
不混入多个阶段的临时字段；
不暴露外部 API 的原始杂字段；
不为了某个页面的临时展示污染核心结构。
```

### 4.2 弱契约信号

以下情况说明数据契约可能过弱：

```text
大量字段都是可选；
后续代码到处 .get()；
同一个事实有多个字段名；
不同阶段共用一个大而全对象；
前端需要知道后端内部字段；
业务层需要知道第三方 API 原始字段；
字段含义依赖注释才能理解；
改一个字段要改很多文件。
```

### 4.3 阶段性数据结构

复杂流程中，不要强行用一个对象覆盖所有阶段。

更清楚的做法是区分阶段：

```text
外部原始结果
→ 内部候选对象
→ 候选证据对象
→ 审阅结果对象
→ 展示对象
```

每个阶段的对象都应说明：

```text
属于哪个阶段；
谁创建；
谁消费；
是否可以跨层传递；
是否可持久化；
是否只是临时展示结构。
```

## 5. 格式转换审查

AI 写代码时很容易出现格式转换噪音。

常见转换包括：

```text
dict → schema object
schema object → dict
ORM object → schema object
external JSON → internal model
internal model → response payload
response payload → frontend dict
frontend dict → view model
enum/status → display label
raw text → escaped HTML
```

### 5.1 每次转换都必须回答

```text
从什么格式变成什么格式？
为什么需要转换？
谁需要转换后的格式？
转换发生在正确的边界吗？
转换后字段是否丢失？
是否只是为了适配某个写得不好的函数？
能不能少转一次？
```

### 5.2 警惕反复转换

需要警惕这种路径：

```text
schema object
→ dict
→ schema object
→ dict
→ 再进入展示层
```

有些转换是必要的，例如：

```text
跨 API 边界要转 JSON；
复制对象并更新字段要转 dict 或使用 copy/update；
展示层需要人类可读 label；
持久化层需要 ORM 对象。
```

但如果转换只是为了让某个函数方便取值，就要检查是否函数接口设计不合理。

### 5.3 转换应集中在边界

优先在这些位置转换：

```text
API client
adapter
normalize 函数
schema / DTO
serializer
view model builder
response builder
database mapper
```

避免在核心业务函数内部散落大量格式转换。

## 6. 中间变量审查

中间变量不是越少越好。好变量能表达阶段，坏变量只是 AI 生成痕迹。

### 6.1 好的中间变量

好的中间变量至少满足一条：

```text
表达一个领域概念；
标记一个处理阶段；
后续会复用；
缩短过长表达式；
帮助调试关键步骤；
让数据流更清楚。
```

示例：

```python
line_text_by_no = _build_line_index(poem)
valid_candidates = []
deduplicated_candidates = _remove_truncated_anchors(valid_candidates)
reviewable_evidence = _flatten_reviewable_evidence(candidate)
```

这些变量让读者知道数据处于什么阶段。

### 6.2 坏的中间变量

坏变量通常只是传递痕迹：

```python
data = response.json()
result = data
final_result = result
return final_result
```

或者：

```python
temp = item
new_item = temp
processed_item = new_item
```

这些变量没有引入新含义，只增加阅读负担。

### 6.3 审查问题

看到中间变量时问：

```text
这个变量表达了新概念吗？
它是否标记了阶段边界？
它是否被复用？
它是否只是为了接住上一行？
它的生命周期是否过长？
它是否定义后隔很远才用？
它是否可以内联？
```

## 7. 函数参数与返回值审查

数据流在函数之间最常见的表现，就是参数和返回值。

### 7.1 参数过多是耦合信号

警惕：

```python
_do_step(a, b, c, d, e, f, state, config, errors)
```

这说明函数依赖太多外部上下文。

可能原因：

```text
抽错函数；
职责不独立；
缺少稳定数据结构；
应该传一个对象而不是一串字段；
应该留在原地而不是强行抽出；
应该拆成两个阶段；
状态不应在这里修改。
```

### 7.2 返回值过绕是契约不清

警惕：

```text
返回 tuple，但调用方靠位置猜含义；
返回 dict，但字段没有契约；
返回对象里混入展示字段、业务字段、错误字段；
函数一会儿返回 list，一会儿返回 None，一会儿返回 dict；
函数同时返回结果和修改外部状态。
```

### 7.3 推荐做法

函数接口应尽量清楚：

```text
输入：一个稳定对象或少量明确参数。
输出：一个稳定结果。
副作用：如果有，必须明确。
错误：是抛出、返回错误对象、降级，还是跳过。
```

### 7.4 审查问题

```text
这个函数真正需要这些参数吗？
能不能传一个更稳定的结构？
返回值是否需要调用方猜字段？
是否同时返回数据又修改状态？
是否把错误信息混在正常数据里？
```

## 8. 数据泄漏审查

数据泄漏指某一层知道了另一层不该知道的内部格式。

### 8.1 外部 API 原始结构泄漏

不理想：

```text
业务层直接依赖第三方 API 的原始字段名；
展示层直接读取第三方 API 的嵌套结构；
多个模块都知道外部返回的 raw shape。
```

推荐：

```text
第三方 API raw response
→ client / adapter / normalize
→ 内部稳定 Evidence / Candidate / Result 对象
→ 业务层使用内部对象
→ 展示层使用展示对象
```

### 8.2 数据库结构泄漏

不理想：

```text
前端知道数据库字段；
展示层依赖 ORM relationship；
业务层把 ORM 对象原样传到远处；
prompt builder 直接依赖数据库表结构细节。
```

推荐：

```text
数据库 ORM
→ service / serializer / schema
→ 内部对象或 API response
→ 下游使用稳定契约
```

### 8.3 展示结构泄漏

不理想：

```text
后端为了某个按钮直接返回 UI 控件字段；
业务层生成 HTML；
核心 service 知道 tabs、popover、CSS class；
前端状态字段进入后端业务。
```

推荐：

```text
后端返回语义数据；
前端决定如何展示；
展示层负责 label、HTML、布局和样式。
```

### 8.4 审查问题

```text
这个模块是否知道了不该知道的字段？
外部 raw 是否传得太远？
ORM 是否传得太远？
UI 展示需求是否污染了核心业务结构？
某个字段名改变会不会影响多个不相关层？
```

## 9. 状态流动审查

状态是跨步骤保存的数据。它比普通变量更容易造成混乱。

### 9.1 需要追踪的问题

```text
这个状态是谁写入的？
谁读取它？
什么时候初始化？
什么时候清空？
什么时候过期？
它依赖哪个对象？
切换对象时是否要重置？
它和其他状态是否表达同一事实？
```

### 9.2 状态重复保存

警惕同一事实存多份：

```text
selected_id
selected_item
selected_text
selected_line_no
current_item_cache
```

这些可能都合理，但必须知道：

```text
谁是主状态？
谁是派生状态？
派生状态是否会过期？
主状态变化时派生状态是否清理？
```

### 9.3 状态清理

用户切换对象、页面、模式、查询条件时，应清理依赖旧对象的状态。

例如：

```text
切换当前作品
→ 清空选中文本
→ 清空旧的阅读辅助结果
→ 清空旧的候选审阅结果
→ 停止自动播放
```

### 9.4 审查问题

```text
状态是否集中管理？
状态清理是否散落在多个 UI 函数里？
是否存在旧状态污染新对象？
是否存在缓存和当前选择不一致？
状态名是否表达真实含义？
```

## 10. 数据库查询与持久化审查

数据流动不仅发生在函数之间，也发生在数据库查询和对象映射之间。

### 10.1 查询形状

审查：

```text
是否只查询当前功能需要的数据？
是否预加载后续一定会访问的关系？
是否可能出现 N+1 查询？
是否把过大的 ORM 对象传给远处函数？
是否查询了很多字段但只用一两个？
是否为了展示层需求改动了持久化结构？
```

### 10.2 ORM 对象边界

ORM 对象适合在数据访问层、服务层短距离使用。  
不适合无边界地传到展示层、prompt 层或远处工具层。

审查：

```text
ORM 对象在哪里进入流程？
在哪里转成 schema / DTO / dict？
是否有明确转换点？
是否有隐藏懒加载风险？
```

### 10.3 写入与事务

审查：

```text
多个写入是否在同一事务中？
中途失败是否会留下半成品？
写入函数是否清楚区分构造对象、flush、commit？
是否把持久化副作用藏在看似纯处理函数里？
```

## 11. 外部服务数据审查

外部服务通常是最脏的数据来源之一。

### 11.1 外部服务返回不稳定

可能问题：

```text
字段缺失；
嵌套结构变化；
返回空列表；
返回字符串而不是对象；
HTTP 404；
超时；
非 JSON；
局部失败；
同一接口不同情况下返回不同 shape。
```

### 11.2 适配层职责

外部服务适配层应负责：

```text
发送请求；
处理网络错误；
处理 HTTP 状态；
解析 JSON；
拆开嵌套；
清理 raw；
转换为内部窄字段；
保留必要 raw 仅供调试；
把错误转成稳定异常或结果状态。
```

### 11.3 不要让 raw 传太远

允许：

```text
raw 保留在 evidence.raw 中供调试；
raw 留在 adapter 内部；
raw 只在日志或调试页面使用。
```

不推荐：

```text
核心业务依赖 raw["SomeNested"]["UnstableField"]；
前端直接展示 raw；
多个模块各自解析 raw。
```

## 12. 展示数据审查

展示层需要的数据和业务层需要的数据不完全一样。

### 12.1 展示层可以做

```text
状态码转中文 label；
时间、标题、来源格式化；
长文本截断；
HTML escape；
空状态展示；
错误提示文案；
tabs / cards / popover 的数据组织。
```

### 12.2 展示层不宜做

```text
深度业务判断；
外部原始数据解析；
数据库对象处理；
模型输出校验；
复杂证据分类；
核心规则排序。
```

### 12.3 View Model / 展示对象

如果展示层开始到处拼字段，可以考虑建立展示前整理函数：

```text
_organize_aids_data(data)
_build_candidate_display_payload(candidate)
_build_review_display_items(review)
```

注意：这不是为了“高级”，而是为了让展示函数只展示，不承担太多数据整理。

## 13. 耦合风险审查

数据流最能暴露耦合。

### 13.1 高耦合信号

```text
一个字段改名要改很多层；
一个模块必须知道另一个模块的内部 dict 结构；
前端知道后端 service 内部字段；
service 知道 UI 展示细节；
多个函数共享可变 dict 并逐步追加字段；
同一个数据在不同地方有不同解释；
状态变化牵动多个不相关函数；
一个函数返回大而全 payload，调用方各取所需。
```

### 13.2 低耦合信号

```text
跨层传递稳定契约；
外部 raw 在边界被转换；
核心业务使用内部对象；
展示层使用展示对象；
字段生成和消费位置清楚；
状态有主状态和派生状态区分；
错误格式稳定；
改一个字段影响范围可预测。
```

### 13.3 审查问题

```text
如果这个字段改名，会影响哪些文件？
如果外部 API 返回变了，谁需要改？
如果页面展示变了，后端是否需要改？
如果数据库字段变了，前端是否需要知道？
```

## 14. AI 常见数据流动问题

AI 生成代码时，特别容易出现以下问题。

### 14.1 数据传递痕迹

```python
payload = raw
data = payload
result = data
return result
```

### 14.2 格式反复横跳

```text
dict → object → dict → object → dict
```

### 14.3 到处猜字段

```python
name = item.get("name") or item.get("title") or item.get("label") or "未知"
```

这可能是必要兼容，也可能说明边界没有统一 normalize。

### 14.4 大而全 payload

一个函数返回所有可能字段，调用方各取所需。短期方便，长期弱契约。

### 14.5 共享可变 dict

多个函数逐步往同一个 dict 塞字段，最后没人知道字段在哪里生成。

### 14.6 错误混入正常数据

例如：

```text
正常结果 list 中塞 error dict；
某个字段有时是数据、有时是错误字符串；
返回 None 表示失败，但调用方不知道原因。
```

### 14.7 UI 字段污染业务对象

例如业务对象里出现：

```text
expanded
tab_label
button_key
css_class
display_color
```

这些通常应在展示层生成。

## 15. Review 检查清单

作为数据流动审查员，按以下清单检查。

### 15.1 来源与可信度

```text
1. 数据从哪里来？
2. 来源是否可信？
3. 不可信数据在哪里校验？
4. 校验后是否变成稳定内部结构？
```

### 15.2 契约

```text
1. 当前数据对象有哪些字段？
2. 哪些字段必填，哪些可选？
3. 谁生成这些字段？
4. 谁消费这些字段？
5. 是否有字段只为某一层临时服务？
```

### 15.3 转换

```text
1. 每次转换是否必要？
2. 是否存在 object / dict 反复转换？
3. 转换是否集中在边界？
4. 是否有字段在转换中丢失或变义？
```

### 15.4 中间变量

```text
1. 中间变量是否有语义价值？
2. 是否只是 AI 传递痕迹？
3. 生命周期是否过长？
4. 是否定义后隔很远才使用？
```

### 15.5 参数与返回值

```text
1. 函数参数是否过多？
2. 是否可以传稳定对象而不是一串字段？
3. 返回值是否稳定？
4. 是否同时返回数据又修改外部状态？
```

### 15.6 泄漏

```text
1. 外部 API raw 是否传太远？
2. ORM / 数据库结构是否传太远？
3. UI 展示结构是否污染业务层？
4. 前后端是否依赖彼此内部细节？
```

### 15.7 状态

```text
1. 状态是谁写入、谁读取？
2. 切换对象时是否清理旧状态？
3. 是否重复保存同一事实？
4. 主状态和派生状态是否清楚？
```

### 15.8 耦合

```text
1. 改一个字段会影响多少文件？
2. 调用方是否依赖被调用方内部结构？
3. 不同模块是否通过大 dict 隐式通信？
4. 是否存在牵一发动全身的数据链？
```

## 16. Review 输出格式

当你作为 Data Flow Reviewer 审查时，按以下结构输出。

```text
## 1. 总体判断

这段代码的数据流是清楚、稳定、必要的吗？
是否存在明显绕路、反复转换或高耦合？

## 2. 数据主线

用箭头图说明核心数据流：

来源
→ 校验 / 转换
→ 内部结构
→ 处理
→ 输出 / 展示

## 3. 契约判断

- 当前核心数据对象是什么？
- 字段由谁生成？
- 字段由谁消费？
- 契约是否稳定？

## 4. 转换判断

- 哪些转换是必要的？
- 哪些转换可疑？
- 是否存在 object / dict 反复横跳？

## 5. 中间变量判断

- 哪些变量有语义价值？
- 哪些变量只是传递痕迹？

## 6. 泄漏与耦合判断

- 是否有外部 raw / ORM / UI 结构泄漏？
- 改字段的影响范围是否过大？

## 7. 最值得修的 1–3 个问题

只列最影响理解和维护的问题。

## 8. 给施工 AI 的最小修改指令

如果需要修，请给小范围、不新增功能、不改外部行为的指令。
```

## 17. 给施工 AI 的数据流约束提示词

可以直接复制给施工 AI：

```text
请按“数据流清楚、契约稳定、转换必要”的原则修改代码。

要求：
1. 先说明本次核心数据从哪里来，到哪里去。
2. 不要制造无意义中间变量。
3. 中间变量必须表达领域概念、阶段边界、复用价值或调试价值。
4. 不要让 dict / object / schema 反复互转；每次转换都必须说明原因。
5. 外部 API、模型输出、用户输入、数据库读取等不可信数据，只在边界处校验和 normalize。
6. 内部流程应尽量使用稳定结构，不要到处 .get() / fallback。
7. 不要让外部 raw、数据库 ORM、UI 展示结构穿透到不该知道它们的层。
8. 函数参数不要过多；如果要传很多字段，检查是否需要稳定数据结构，或是否抽错函数。
9. 状态写入和清理必须集中，不要散落在多个渲染函数里。
10. 不新增未要求功能，不改变外部接口，不改变数据结构，除非明确说明并得到确认。

完成后请输出：
- 核心数据流箭头图；
- 哪些数据结构被保留；
- 是否新增转换；
- 是否删除无意义变量；
- 如何验证行为不变。
```

## 18. 给 Review AI 的数据流审查提示词

可以直接复制给 Review AI：

```text
请按“数据流动与数据契约审查”来 review 这段代码。

你不负责新增功能，也不负责大重构。你的任务是判断：
1. 数据从来源到消费是否清楚；
2. 每次格式转换是否必要；
3. 是否存在无意义中间变量；
4. 是否存在 dict / object / schema 反复转换；
5. 是否存在外部 raw、ORM、UI 结构泄漏；
6. 函数参数和返回值是否清楚；
7. 状态写入、读取、清理是否集中；
8. 改一个字段是否会牵动多个模块。

请输出：
- 核心数据流箭头图；
- 最明显的数据流问题 1–3 个；
- 哪些转换是必要的，哪些可疑；
- 给施工 AI 的最小修改指令。

不要泛泛说“降低耦合”，必须具体到变量、字段、函数、数据结构或状态。
```

## 19. 和其他 Skill 的配合

### 19.1 和抽象层级 Skill

抽象层级 Skill 判断：

```text
函数 / 模块 / 文件夹是否该这样拆。
```

Data Flow Skill 判断：

```text
拆完之后，数据是否还走得清楚。
```

### 19.2 和 Code Explainer Skill

Code Explainer 负责把数据流讲给人听。  
Data Flow Reviewer 负责判断数据流是否应该被简化。

### 19.3 和测试 Skill

测试 Skill 应优先保护：

```text
数据转换；
normalize；
schema 校验；
状态清理；
外部失败降级；
关键字段不丢失。
```

### 19.4 和开发原则 Skill

开发原则是总纲。  
Data Flow Skill 是其中“数据路径、契约和转换”的专门审查工具。

## 20. 最终目标

这个 Skill 的最终目标不是让代码变得“更抽象”，而是让数据在项目里保持清楚身份。

成功的数据流应该是：

```text
来源清楚；
校验位置清楚；
结构稳定；
转换必要；
传递范围合理；
状态生命周期明确；
字段影响范围可预测；
项目负责人能说清楚数据从哪里来、到哪里去、为什么要变。
```

失败的数据流通常是：

```text
到处都是 dict；
到处都是 .get()；
到处都是临时变量；
到处都在转换；
外部 raw 到处传；
状态到处写；
字段在哪里生成没人知道；
改一个字段牵一发动全身。
```

最重要的一句话：

> 好的数据流不是“每一步都能跑”，而是每一步都能说清楚：这个数据现在是谁、为什么变、要去哪里。
