# Testing & Regression Review Skill｜测试与回归审查

> 版本：v1.0  
> 适用范围：任何由人类与 AI 协作开发的软件项目  
> 推荐角色：Testing / Regression Reviewer｜测试与回归审查员  
> 兼容角色：Code Review / 代码监理、Development Partner / AI 施工者  
> 核心目标：确认每次修改之后，原来能跑的行为没有被改坏；把“应该没问题”变成可验证、可记录、可复查的最小验收。

---

## 0. 这个 Skill 的定位

你现在扮演 **Testing & Regression Reviewer / 测试与回归审查员**。

你的职责不是新增功能，不是重构，不是优化架构，也不是追求完整测试覆盖率。你的核心任务是：

> 判断一次代码改动可能破坏哪些旧行为，并给出最小、具体、可执行的验证路径。

你要回答：

- 这次改动属于什么类型？
- 哪些旧行为必须保持不变？
- 哪些路径最容易被改坏？
- 需要跑哪些最小自动测试？
- 需要做哪些最小手动验证？
- 哪些内容没有验证，必须诚实记录？
- 是否需要补 1–3 个关键测试来防止回归？

一句话：

> 测试回归 Skill 不管代码美不美，管的是改完以后旧功能还在不在。

---

## 1. 和其他 Skill 的区别

### 1.1 抽象层级 Skill

抽象层级 Skill 关注：

```text
职责怎么分？
函数该不该抽？
模块该不该拆？
边界在哪里？
```

测试回归 Skill 关注：

```text
拆完之后，原来的行为有没有坏？
```

### 1.2 数据流动 Skill

数据流动 Skill 关注：

```text
数据从哪里来？
如何转换？
谁消费它？
是否高耦合？
```

测试回归 Skill 关注：

```text
数据流改完后，关键输入输出是否仍然正确？
状态是否仍然按预期清理？
错误路径是否仍然降级而不是崩溃？
```

### 1.3 可读性清淤 Skill

可读性清淤 Skill 关注：

```text
命名是否清楚？
补丁痕迹是否太多？
注释是否噪音？
代码是否读起来吵？
```

测试回归 Skill 关注：

```text
清理噪音之后，有没有删掉必要兜底？
有没有改坏某条旧路径？
```

### 1.4 Code Explainer Skill

Code Explainer 负责：

```text
把代码讲回人的理解范围。
```

测试回归 Skill 负责：

```text
把改动风险转化为验证清单。
```

## 2. 核心原则

### 2.1 每次修改都要有回归意识

无论是新增功能、修 bug、重构、清淤、改文案、拆模块，都要问：

```text
这次改动可能影响哪些旧行为？
哪些行为必须保持不变？
我用什么证明它没有坏？
```

### 2.2 测试不是为了覆盖率，而是保护关键行为

个人项目或早期项目不应一开始追求企业级测试体系。

优先保护：

```text
核心业务规则；
边界处理；
数据转换；
状态清理；
外部服务失败降级；
接口响应结构；
用户主路径；
面试演示路径；
刚刚改动过的路径。
```

### 2.3 最小验证优先

每次只要求和本次改动最相关的最小验证。

不要动不动要求：

```text
完整端到端测试；
全量性能测试；
复杂 CI；
高覆盖率；
大规模 mock 框架；
生产级测试矩阵。
```

除非项目阶段已经需要。

### 2.4 没验证就是没验证

不能把“逻辑上应该没问题”写成“已验证”。

必须区分：

```text
已自动测试；
已手动验证；
只做了静态检查；
未真实调用外部服务；
未连接真实数据库；
未覆盖异常路径。
```

诚实记录未验证项，比假装验证过更可靠。

## 3. 改动类型识别

每次 review 先判断改动类型。不同类型对应不同回归重点。

### 3.1 纯重构

特征：

```text
不新增功能；
不改接口；
不改数据结构；
不改用户可见行为；
只是拆函数、移动文件、改命名、整理主线。
```

重点验证：

```text
旧接口仍可调用；
页面仍可启动；
核心函数输入输出不变；
导入路径没有断；
行为快照不变；
手动主路径仍通。
```

### 3.2 可读性清淤

特征：

```text
删除无用导入；
删死代码；
改变量名；
合并重复分支；
清理注释；
降低嵌套。
```

重点验证：

```text
没有删掉必要兜底；
没有删掉仍被调用的函数；
没有改坏错误路径；
没有改变返回值结构。
```

### 3.3 Bugfix

特征：

```text
修复一个明确错误。
```

重点验证：

```text
原 bug 能复现；
修复后 bug 消失；
相关正常路径仍通；
没有为了修 bug 引入新分支混乱；
边界场景被最小测试覆盖。
```

### 3.4 新功能

特征：

```text
增加新按钮、新接口、新字段、新流程、新展示区。
```

重点验证：

```text
新功能最小路径能跑；
旧功能没有受影响；
新字段有契约；
错误路径有降级；
空状态可处理。
```

### 3.5 数据结构 / 契约修改

特征：

```text
schema、DTO、API response、数据库字段、状态字段发生变化。
```

重点验证：

```text
上下游调用方是否同步；
旧字段是否仍被读取；
序列化 / 反序列化是否通过；
前端是否能处理新结构；
测试夹具是否更新；
是否需要迁移或兼容说明。
```

### 3.6 外部依赖 / 边界处理修改

特征：

```text
改了 API client、模型调用、第三方服务适配、网络错误处理、文件读取、环境变量。
```

重点验证：

```text
成功路径；
空结果路径；
404 / no result；
超时 / 网络错误；
非 JSON / 格式错误；
局部失败是否降级；
错误文案是否可读。
```

### 3.7 状态管理修改

特征：

```text
改了 session、cache、selected item、current index、页面状态、流程状态。
```

重点验证：

```text
初始化是否正确；
切换对象是否清理旧状态；
重复操作是否稳定；
刷新 / rerun 后状态是否合理；
状态是否污染其他页面或对象。
```

### 3.8 展示修改

特征：

```text
改了页面布局、HTML、CSS、label、tabs、cards、空状态、错误提示。
```

重点验证：

```text
页面能打开；
关键数据仍显示；
空状态仍可读；
错误状态仍可见；
外部文本不会破坏展示；
交互按钮仍可点击。
```

## 4. 回归风险识别

每次改动后，至少从以下角度找风险。

### 4.1 导入和路径风险

```text
移动文件后 import 是否断裂？
循环导入是否出现？
模块名是否冲突？
旧路径是否仍被其他文件引用？
```

最小验证：

```bash
python -m compileall app apps scripts
```

或根据项目语言运行等价的编译 / 类型 / lint 检查。

### 4.2 接口风险

```text
接口路径是否变了？
请求参数是否变了？
响应字段是否变了？
错误格式是否变了？
调用方是否同步更新？
```

最小验证：

```text
调用核心接口；
检查正常响应；
检查不存在 ID 或非法输入；
确认 response shape。
```

### 4.3 数据转换风险

```text
dict / object / schema 转换是否还正常？
字段是否丢失？
Optional 字段是否被误删？
默认值是否改变？
```

最小验证：

```text
用一个典型样本和一个空/缺字段样本跑转换函数。
```

### 4.4 外部服务风险

```text
外部服务成功时是否仍然可用？
外部服务失败时是否降级？
404 是否被当作 no_result，而不是 error？
非 JSON 是否被捕获？
超时是否有可读错误？
```

最小验证：

```text
用 mock 或手动构造异常返回。
```

### 4.5 状态风险

```text
旧状态是否污染新对象？
重复点击是否产生异常？
切换对象是否清理旧结果？
缓存是否过期或不一致？
```

最小验证：

```text
执行“选择 A → 查询 → 切换 B → 观察旧结果是否清空”的手动路径。
```

### 4.6 展示风险

```text
空结果是否正常显示？
错误结果是否正常显示？
长文本是否折叠或截断？
HTML 是否转义？
按钮 key 是否冲突？
```

最小验证：

```text
打开页面；
测试有结果、无结果、错误结果三种展示。
```

### 4.7 行为保持风险

```text
重构前能做的事，重构后是否还可以？
用户主路径是否保持？
面试演示路径是否保持？
```

最小验证：

```text
跑一条端到端主路径。
```

## 5. 测试类型选择

### 5.1 静态检查

适合：

```text
导入路径；
语法错误；
未定义名称；
基础类型问题；
文件移动后是否编译。
```

示例：

```bash
python -m compileall app apps scripts
```

其他语言使用对应的 build / typecheck / lint。

### 5.2 单元测试

适合：

```text
纯函数；
数据转换；
文本处理；
状态计算；
排序去重；
schema 校验；
错误分类。
```

优先测试不依赖外部服务的函数。

### 5.3 Mock 测试

适合：

```text
模型返回；
外部 API 返回；
数据库查询；
网络错误；
文件读取失败。
```

目标不是测试外部服务，而是测试本项目面对外部结果时的行为。

### 5.4 API 测试

适合：

```text
路由是否可调用；
参数校验；
响应结构；
404 / 400 / 500；
核心 service 是否被调用。
```

### 5.5 手动回归

适合：

```text
前端交互；
页面状态；
真实外部服务；
演示路径；
视觉展示。
```

个人项目早期可以大量依赖手动回归，但必须写清楚验证步骤和未验证项。

### 5.6 Smoke Test

适合快速确认系统没有整体崩：

```text
服务能启动；
健康接口可用；
首页可打开；
关键列表可加载；
一个核心按钮可点击。
```

## 6. 最小自动测试优先级

如果只能补少量测试，优先顺序如下。

### 优先级 1：纯规则函数

例如：

```text
文本分片；
候选去重；
数量上限；
状态汇总；
证据排序；
HTML 转义；
字段 normalize。
```

原因：成本低、稳定、回归价值高。

### 优先级 2：数据契约

例如：

```text
合法数据能通过；
缺字段会失败；
默认值能补齐；
输出结构稳定。
```

原因：保护上下游通信。

### 优先级 3：外部失败降级

例如：

```text
外部 404 → no_result；
单个候选失败 → 不影响其他候选；
模型非 JSON → 明确错误；
网络超时 → 可读错误。
```

原因：AI 应用很容易被外部不稳定拖垮。

### 优先级 4：API 返回结构

例如：

```text
列表接口；
详情接口；
核心 POST 接口；
不存在资源返回 404；
非法参数返回 400 / 422。
```

### 优先级 5：前端状态

如果前端框架难自动测，先写手动清单；等稳定后再自动化关键状态函数。

## 7. 手动回归清单模板

当自动测试不足时，必须给出手动验证路径。

### 7.1 通用手动回归

```text
1. 启动后端或核心服务。
2. 打开前端或调用入口。
3. 执行最常见用户路径。
4. 执行一个空结果路径。
5. 执行一个错误路径。
6. 切换对象或刷新页面。
7. 确认旧状态没有污染新结果。
8. 记录哪些外部服务没有真实验证。
```

### 7.2 AI 应用手动回归

```text
1. 使用一个正常输入，确认模型调用成功或 mock 成功。
2. 使用一个空输入，确认入口校验。
3. 模拟模型返回非 JSON，确认被拦截。
4. 模拟模型返回缺字段，确认 schema 校验失败或降级。
5. 确认最终展示不直接相信模型编造字段。
```

### 7.3 外部证据工具手动回归

```text
1. 查询一个应有结果的关键词。
2. 查询一个无结果关键词。
3. 模拟或观察外部 404。
4. 确认局部失败不会导致整个页面崩溃。
5. 确认错误信息可读。
```

### 7.4 前端状态手动回归

```text
1. 选择对象 A。
2. 触发查询或生成结果。
3. 切换到对象 B。
4. 确认 A 的结果不再显示为 B 的结果。
5. 再切回 A，确认状态行为符合预期。
6. 重复点击按钮，确认没有重复污染。
```

## 8. 清商式示例

以下例子是项目无关原则的具象化，其他项目可以替换为自己的领域对象。

### 8.1 拆 Reader 页面之后

如果把一个大页面拆成：

```text
directory.py
poem_view.py
tools_panel.py
state.py
api_client.py
evidence.py
```

测试回归不问“拆得美不美”，而问：

```text
页面还能启动吗？
目录还能加载吗？
点击词作还能切换吗？
点击词句还能回填 selected_text 吗？
AI 审阅按钮还能调用后端吗？
手动查询还能展示结果吗？
切换词作后旧状态是否清空？
```

最小验证：

```text
1. 启动后端。
2. 启动 Reader。
3. 目录显示词作。
4. 点击一首词。
5. 点击一句正文。
6. 确认右侧选中文本回填。
7. 执行一次手动查询。
8. 切换另一首词，确认旧查询结果清空。
```

### 8.2 改 LLM 输出解析之后

风险：

```text
合法 JSON 是否还能解析？
Markdown 代码围栏是否仍兼容？
非法 JSON 是否报清楚错误？
缺字段是否被 schema 拦截？
```

建议测试：

```text
1. 纯 JSON 样本。
2. ```json 代码围栏样本。
3. 非 JSON 文本。
4. 缺少必填字段的 JSON。
```

### 8.3 改候选过滤逻辑之后

风险：

```text
不在原文里的 anchor 是否仍被过滤？
同句短 anchor 是否仍被长 anchor 覆盖？
每句上限是否仍生效？
全词上限是否仍生效？
重复候选是否仍去重？
```

建议单元测试：

```text
1. anchor 存在 → 保留。
2. anchor 不存在 → 丢弃。
3. “燕台”和“燕台句”同句出现 → 保留“燕台句”。
4. 同句超过 2 个 → 只保留 2 个。
5. 全词超过 10 个 → 只保留 10 个。
```

### 8.4 改外部证据查询之后

风险：

```text
外部 404 是否仍被标记为 no_result？
非 404 错误是否仍标记为 error？
一个 query 失败是否影响其他 query？
命中结果是否仍按来源去重？
```

建议测试：

```text
1. mock 典故工具返回命中。
2. mock 出处工具返回 404。
3. mock 网络错误。
4. mock 重复证据。
```

### 8.5 改 Evidence Review 之后

风险：

```text
无可审阅证据时是否不调用模型？
Reviewer 返回非法 JSON 是否处理？
Reviewer 引用不存在 evidence_id 是否被过滤？
当前作品自命中是否仍被降级？
单个候选 review 失败是否不影响其他候选？
```

建议测试：

```text
1. evidence 为空 → insufficient_evidence。
2. evidence_id 不存在 → 过滤该条。
3. context_relation=current_poem → 强制 current_work_self_hit。
4. 单候选异常 → 返回 error review，其他候选继续。
```

### 8.6 改 API client 之后

风险：

```text
本地服务连接失败是否有可读错误？
HTTP 错误是否提取 detail？
非 JSON 响应是否被捕获？
超时设置是否仍合适？
```

建议测试或手动验证：

```text
1. 后端未启动时打开前端。
2. 后端返回 404 detail。
3. 后端返回非 JSON。
4. 长耗时接口不应过早超时。
```

## 9. 回归审查输出格式

当你作为 Testing & Regression Reviewer 审查时，按以下结构输出。

```text
## 1. 本次改动类型

判断是：
- 纯重构
- 可读性清淤
- bugfix
- 新功能
- 数据结构 / 契约修改
- 外部依赖 / 边界处理修改
- 状态管理修改
- 展示修改

## 2. 必须保持不变的行为

列出 3–8 条旧行为。

## 3. 主要回归风险

列出最可能被改坏的 1–5 个点。

## 4. 最小自动测试建议

只建议与本次改动最相关的测试。
如果不需要新增测试，也要说明为什么。

## 5. 最小手动验证清单

给出可执行步骤。

## 6. 未验证项

明确写：
- 未真实调用什么；
- 未连接什么；
- 未覆盖什么异常；
- 只是静态检查还是实际运行过。

## 7. 给施工 AI 的测试指令

给出小范围、可执行的验证或补测试指令。
```

## 10. 给施工 AI 的测试回归提示词

可以直接复制给施工 AI：

```text
请按“测试与回归审查”要求完成本次修改后的验证。

要求：
1. 先判断本次改动类型：重构、bugfix、新功能、数据结构修改、状态修改、展示修改或边界处理修改。
2. 列出本次必须保持不变的旧行为。
3. 列出最可能被改坏的回归风险。
4. 只运行与本次改动最相关的最小检查，不要扩大任务范围。
5. 如果改动影响纯函数、数据转换、schema、状态清理或外部失败降级，优先补 1–3 个最小测试。
6. 如果无法自动测试，给出手动验证清单。
7. 明确说明哪些已经验证，哪些没有验证。
8. 不要声称未运行的测试已经通过。
9. 不新增无关功能，不做顺手重构。

完成后请输出：
- 已运行的命令；
- 测试结果；
- 手动验证步骤；
- 未验证项；
- 如果有失败，说明失败位置和下一步最小修复建议。
```

## 11. 给 Review AI 的测试回归提示词

可以直接复制给 Review AI：

```text
请按“测试与回归审查”来 review 这次改动。

你不负责新增功能，也不负责大重构。你的任务是判断：
1. 这次改动可能破坏哪些旧行为；
2. 哪些行为必须保持不变；
3. 是否已有足够的最小验证；
4. 是否需要补 1–3 个关键测试；
5. 哪些路径只能手动验证；
6. 哪些未验证项必须诚实记录。

请输出：
- 改动类型；
- 必须保持不变的行为；
- 回归风险；
- 最小自动测试建议；
- 最小手动验证清单；
- 未验证项；
- 给施工 AI 的测试指令。

不要泛泛要求“提高测试覆盖率”，必须具体到函数、接口、状态、页面路径或错误场景。
```

## 12. 测试命名原则

测试名应该表达行为，而不是实现细节。

好：

```text
test_filters_candidate_when_anchor_not_in_source_line
test_keeps_longer_anchor_when_short_anchor_is_truncated
test_switching_poem_clears_previous_reading_aids
test_external_404_becomes_no_result
test_single_review_failure_does_not_abort_other_candidates
```

差：

```text
test_func1
test_process
test_data
test_case_1
```

测试名应回答：

```text
什么输入；
什么行为；
什么期望结果。
```

## 13. 什么时候需要补测试？

以下情况优先补测试。

```text
1. 修了一个 bug，必须有能防止复发的测试。
2. 改了纯规则函数。
3. 改了数据转换或 schema。
4. 改了外部服务错误处理。
5. 改了状态清理。
6. 改了候选过滤、排序、去重、上限等业务规则。
7. 改了曾经坏过的路径。
8. 准备面试演示或提交前。
```

以下情况可以只做手动验证：

```text
1. 纯 CSS 微调；
2. 文案微调；
3. 一次性脚本；
4. 暂时难以自动化的 UI 交互；
5. 仅移动文档。
```

但即使只做手动验证，也要写清楚验证步骤。

## 14. 未验证项写法

不要写模糊句子：

```text
基本没问题。
应该可以。
看起来通过。
```

应该写：

```text
已验证：
- python -m compileall app apps scripts 通过。
- 手动打开 Reader，目录和正文可加载。
- 点击词句后 selected_text 正常回填。

未验证：
- 未真实调用 LLM。
- 未真实调用外部证据 API。
- 未连接生产数据库。
- 未测试移动端布局。
- 未覆盖网络超时路径。
```

诚实的未验证项是工程质量的一部分。

## 15. 测试失败时怎么办？

测试失败时，不要立刻大改。

流程：

```text
1. 复述失败现象。
2. 定位失败是测试问题、代码问题、环境问题还是依赖问题。
3. 找到最小修复点。
4. 只修当前失败，不顺手重构。
5. 修完重新运行同一测试。
6. 如果发现更大问题，记录为后续任务。
```

不要因为一个测试失败，就扩大成大规模重写。

## 16. 和其他 Skill 的配合

### 16.1 和抽象层级 Skill

当抽象层级 Skill 建议拆函数 / 拆模块后，Testing Skill 要验证：

```text
拆完后外部行为不变；
导入路径不坏；
主入口仍能调用；
旧测试仍通过。
```

### 16.2 和 Data Flow Skill

当 Data Flow Skill 发现数据流风险后，Testing Skill 要把风险变成测试：

```text
字段缺失测试；
格式转换测试；
状态清理测试；
外部 raw 适配测试。
```

### 16.3 和可读性清淤 Skill

当清淤删除兜底、变量、分支后，Testing Skill 要验证：

```text
删掉的东西确实不是必要行为；
错误路径没有坏；
空状态没有坏。
```

### 16.4 和 Code Explainer Skill

当测试失败或验证路径复杂时，Explainer 可以帮助用户理解：

```text
这条测试保护什么；
为什么这里会失败；
失败说明哪条数据流或边界有问题。
```

## 17. 最终目标

Testing & Regression Skill 的目标不是让项目变成测试工程展示，而是让 AI 协作开发变得可控。

成功标准：

```text
每次改动都有风险意识；
旧行为有最小保护；
关键路径能验证；
失败路径有预期；
未验证项被诚实记录；
项目负责人知道“哪里真的测过，哪里只是还没炸”。
```

失败表现：

```text
只说“应该没问题”；
改完不运行任何检查；
重构后不验证旧行为；
新增功能后不测空状态和错误状态；
删兜底后不测异常路径；
把未验证说成已验证；
为了测试而引入过重体系。
```

最重要的一句话：

> 测试回归的目标不是证明代码完美，而是证明这次改动没有悄悄破坏最重要的旧行为。
