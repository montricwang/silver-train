# Abstraction & Boundary Review Skill｜抽象层级与边界尺度审查

> 版本：v1.0  
> 适用范围：任何由人类与 AI 协作开发的软件项目  
> 推荐角色：Code Review / 代码监理  
> 兼容角色：Development Partner / AI 施工者  
> 核心目标：控制抽象力度、防御边界和职责层级，避免代码在“能跑”的同时变得难读、过度拆分、到处兜底或层级混乱。

---

## 0. 这个 Skill 应该归到哪里？

这个 Skill 最适合放在 **Review Skill / 代码监理** 里。

原因是：抽象层级、边界位置、防御频率这些问题，本质上是代码质量和可维护性问题。它们不一定决定功能能不能跑，却决定项目负责人能不能理解、接管和继续维护。

不过，它也可以作为开发前的约束规则。施工 AI 在写代码之前，可以先读本 Skill 的简短版；Code Review AI 则应使用完整版本做审查。

一句话定位：

> 开发时用它防止写偏；Review 时用它判断代码是否抽象过度、边界混乱、防御污染主线。

---

## 1. 核心判断

抽象不是把代码拆小，而是给一段稳定职责命名。  
边界不是到处加兜底，而是规定哪一层负责校验、转换和信任。

最核心的公式是：

```text
抽象收益 =
  命名带来的理解收益
+ 隐藏细节带来的减负
+ 复用 / 测试 / 替换收益

抽象成本 =
  跳转成本
+ 参数成本
+ 抽象误导成本
+ 文件分散成本
```

只有当抽象收益大于抽象成本时，才值得抽。

同理，防御式编程也不是越多越好：

```text
好的防御：集中在不可信边界，让内部流程更干净。
坏的防御：散落在每一层，让代码到处显得不可信。
```

---

## 2. AI 和人类写代码的重要差异

AI 默认更容易写出“局部完成型代码”：

```text
主线、边界、兼容、未来扩展、错误兜底同时展开。
```

这会导致功能看似完整，但读者很难看到代码的成长顺序。

人类更自然的写法通常是“由核心向外硬化”：

```text
先写最小主线
→ 发现输入不稳定
→ 在入口加校验
→ 发现外部服务会失败
→ 在 client / adapter 层处理异常
→ 发现返回格式混乱
→ 在 normalize / schema 层统一整理
→ 内部流程逐渐变干净
```

AI 常见问题：

```text
1. 每一层都 .get() / fallback / try。
2. 每几行就抽一个函数，但函数名空泛。
3. 看到未来可能性就提前抽模块或类。
4. 把展示、业务、边界、适配混在同一个函数里。
5. 写出很多中间变量，但这些变量没有领域含义。
```

Review 时要特别检查这些 AI 快速生成痕迹。

## 3. 抽象与边界的关系

抽象决定：

```text
谁负责什么？
这段逻辑应该放在哪一层？
它应该被命名成什么？
它和周围代码是什么关系？
```

边界决定：

```text
谁相信什么？
传进来的数据可靠吗？
如果不可靠，谁负责校验？
失败以后是中断、报错、降级，还是跳过？
```

一句话原则：

> 抽象决定“谁负责什么”，边界决定“谁相信什么”。

只要抽出一个函数，就形成了一个小契约。

例如：

```python
deduped = _remove_truncated_anchors(candidates)
```

这背后的契约是：

```text
输入：已经通过基础校验的候选列表。
输出：去掉截断锚点后的候选列表。
负责：处理同句内短 anchor 被长 anchor 覆盖的规则。
不负责：解析 LLM 原始输出、不负责检查 anchor 是否在原文、不负责数量上限。
```

如果这个函数内部继续大量检查 LLM 原始格式，就说明边界混乱了。

## 4. 抽象层级从小到大

同一套原则可以从代码块一路放大到系统架构。

### 4.1 代码块：给人看的分段

代码块没有真正的接口契约，只是让读者知道“这几行属于同一阶段”。

适合：

```text
2–15 行；
逻辑直观；
不值得单独命名；
留在原地更容易读；
只需要一行注释标出阶段。
```

示例：

```python
# 步骤 ①：解析、定位、覆盖理由
parsed = []
for raw in raw_candidates:
    candidate = _try_parse_candidate(raw, line_text_by_no)
    if candidate is not None:
        parsed.append(candidate)
```

这段代码不一定要再抽成 `_parse_candidates()`。读者能看到这里是在逐条解析，轻量细节反而有助于理解。

### 4.2 函数：最小契约单位

函数有名字、输入、输出和职责，是最小的抽象边界。

适合：

```text
有稳定语义块；
能用具体函数名概括；
输入输出自然；
留在主函数会打断主线；
可能被复用、测试、解释或替换。
```

好例子：

```python
line_text_by_no = _build_line_index(poem)
candidate = _try_parse_candidate(raw, line_text_by_no)
deduped = _remove_truncated_anchors(parsed)
limited = _enforce_limits(deduped, max_per_line=2, max_total=10)
```

不好的例子：

```python
result = _handle_results(data)
value = _process_data(item)
payload = _do_step(raw)
```

如果函数名只能叫 `handle`、`process`、`do_step`，通常说明这段逻辑还没有形成真正的语义块。

### 4.3 模块：稳定职责集合

模块不是函数垃圾桶，而是一组围绕同一职责的函数。

适合：

```text
一组函数围绕同一稳定职责；
文件变长但职责可拆；
这些函数共享同一类输入输出或领域概念；
拆出去后项目地图更清楚。
```

示例：

```text
api_client.py：负责前端或上层代码访问接口，不直接处理业务规则。
state.py：负责页面状态或运行状态变化。
text.py：负责文本分片、清理、展示前加工。
evidence.py：负责证据展示 HTML 或 view model。
```

不要按机械控件或微小动作拆模块：

```text
button_helpers.py
caption_helpers.py
popover_helpers.py
if_helpers.py
```

除非这些确实是长期稳定职责，否则会造成文件碎片化。

### 4.4 文件夹 / Package：领域边界

文件夹代表一个子领域，而不是为了“整理得好看”。

适合：

```text
一组模块共同服务一个子系统；
内部文件之间关系紧密；
对外暴露少量入口；
外部不需要知道内部细节。
```

示例：

```text
reader/：阅读器前端内部能力集合。
services/：业务流程集合。
schemas/：数据契约集合。
scripts/：离线工具脚本集合。
tests/：行为验证集合。
```

### 4.5 子系统：运行和组织边界

前端、后端、数据库、外部服务、部署、测试等，是更硬的边界。

这种边界不能随便抽，因为改动成本高。

示例：

```text
前端负责交互和展示。
后端负责业务流程和数据契约。
数据库负责持久化。
外部服务通过 client / adapter 层访问。
运维负责配置、密钥、启动和部署环境。
```

## 5. 抽象升级成本原则

抽象层级越高，越要谨慎。

```text
代码块 → 函数：成本低，可以为可读性灵活抽。
函数 → 模块：成本中等，需要职责稳定。
模块 → 文件夹：成本较高，需要领域稳定。
文件夹 → 子系统：成本高，需要运行边界或组织边界稳定。
```

规则：

> 函数可以为可读性而抽；模块最好因职责稳定而抽；文件夹应该因领域稳定而抽；系统边界必须因运行、部署或团队职责稳定而抽。

AI 常见问题是过早升级抽象：

```text
看到两个函数相关 → 立刻抽模块。
看到几个模块相关 → 立刻建议架构。
看到未来可能性 → 立刻预留接口。
```

Review 时应反问：

```text
这个抽象现在真的稳定了吗？
它解决了当前问题，还是在为想象中的未来服务？
```

## 6. 何时抽函数？

满足以下任一条件，可以考虑抽函数。

### 6.1 复用

同一逻辑出现 2 次或以上。

目的：

```text
减少重复；
统一规则；
避免未来只改一处漏改另一处。
```

### 6.2 命名

虽然只调用一次，但它是一个独立业务步骤，抽出来能让主函数更像目录。

示例：

```python
valid_candidates = _keep_candidates_that_exist_in_source(raw_candidates, source)
deduplicated = _remove_overlapping_candidates(valid_candidates)
return _apply_candidate_limits(deduplicated)
```

### 6.3 隐藏繁琐细节

这段代码虽然只做一步，但内部细节开始遮住主线。

例如内部出现：

```text
多层 try；
多层 if；
字段修正；
错误记录；
排序规则；
日志统计；
兼容旧格式；
多种外部失败处理。
```

### 6.4 可测试 / 可替换 / 可解释

如果某段规则以后可能单独测试、单独解释、单独替换，也适合抽函数。

示例：

```python
_remove_truncated_anchors(candidates)
```

即使只调用一次也值得存在，因为它承载了明确规则：

```text
同句内“燕台”被“燕台句”覆盖时，保留更完整的。
```

## 7. 何时不要抽函数？

以下情况不要机械抽函数。

### 7.1 代码很短且留在原地更直观

示例：

```python
title = poem.get("title")
heading = html.escape(poem.get("tune_name") or "未题词牌")
if title:
    heading = f"{heading} · {html.escape(title)}"
```

如果这几行只在一个地方出现，不一定要抽成 `_build_heading()`。留在原地可能更直观。

### 7.2 函数名空泛

如果只能命名为：

```text
_process_data
_handle_item
_do_step
_prepare_result
```

说明抽象不够清楚。

### 7.3 参数过多

警惕这种函数：

```python
_do_step(a, b, c, d, e, f, state, config, errors)
```

这说明该逻辑和上下文缠得太紧，强行抽出只是把复杂性搬家。

粗略经验：

```text
1–3 个参数：通常自然。
4 个参数：需要警惕。
5 个以上参数：优先考虑是否抽错层级，或是否应该传入更稳定的数据结构。
```

### 7.4 抽出后读者必须频繁跳转

如果读主流程时每两三行就必须跳一次函数，说明抽象太碎。

### 7.5 抽象后没有减少理解成本

如果读者不点进去就看不懂函数名，那么这个函数没有完成“命名即解释”的任务。

## 8. 代码块注释 vs 私有函数

这是两种不同力度。

### 8.1 用代码块注释

适合：

```text
逻辑短；
细节不复杂；
留在原地能帮助理解；
只是主流程中的一个小阶段。
```

示例：

```python
# 步骤 ①：解析、定位、覆盖理由
parsed = []
for raw in raw_candidates:
    candidate = _try_parse_candidate(raw, line_text_by_no)
    if candidate is not None:
        parsed.append(candidate)
```

### 8.2 抽成私有函数

适合：

```text
这段逻辑内部开始复杂；
它有清楚的业务名字；
它值得单独测试或替换；
留在主函数会打断叙事。
```

示例：

```python
parsed = _parse_valid_candidates(raw_candidates, line_text_by_no)
```

### 8.3 判断方法

问自己：

```text
这段代码留在这里，是让主线更清楚，还是让主线变浑？
抽出去以后，是让主线更清楚，还是只是增加跳转？
```

主函数不是越短越好，而是越能表达流程越好。

## 9. 抽象层级一致原则

一个函数内部可以有多步，但这些步骤应处于同一抽象层级。

可以接受：

```python
messages = build_prompt(poem)
raw_text = await chat_completion(messages)
json_text = extract_json(raw_text)
data = json.loads(json_text)
analysis = AnalysisSchema.model_validate(data)
return analysis
```

因为每一步都在“分析流程”的同一层级。

不太好：

```python
messages = build_prompt(poem)
headers = {"Authorization": "..."}
async with http_client(...) as client:
    response = await client.post(url, headers=headers, json=payload)
data = response.json()
analysis = AnalysisSchema.model_validate(data)
return analysis
```

这里混了业务流程和 HTTP 细节。HTTP 细节应该下沉到 client / adapter 层。

规则：

> 一个函数里可以有多步，但不要一会儿是业务流程，一会儿是底层请求细节，一会儿又是展示拼接。

## 10. 边界防御原则

防御式编程应集中在不可信边界。

### 10.1 不可信边界包括

```text
用户输入；
外部请求；
模型原始返回；
第三方 API 返回；
数据库读取；
文件读取；
环境变量；
历史缓存；
跨系统传入的数据；
前后端通信；
部署环境。
```

这些地方可以校验、兜底、try/except、默认值、降级和结构化错误。

### 10.2 内部流程要相信契约

一旦数据通过边界校验，内部流程应尽量使用稳定结构。

不要在内部到处写：

```python
candidate.get("anchor_text") or ""
candidate.get("line_no") or 0
candidate.get("query_variants") or []
```

如果字段可能缺失，优先在边界处处理：

```text
schema；
normalize 函数；
API client；
adapter；
入口校验；
数据库查询返回转换；
view model 构造。
```

原则：

> 防御要放在边界，内部要相信契约。

## 11. 边界防御的清商式例子

以下例子是项目无关原则的具象化，其他项目可替换成自己的领域对象。

### 11.1 LLM 输出边界

```python
def _try_parse_candidate(raw, line_text_by_no):
    try:
        candidate = CandidateSchema.model_validate(raw)
    except ValidationError:
        return None

    source_line = line_text_by_no.get(candidate.line_no)
    if not source_line or candidate.anchor_text not in source_line:
        return None

    return candidate.model_copy(update={"line_text": source_line})
```

这里适合防御，因为输入是模型原始输出，不可信。

它负责：

```text
原始 dict → 结构化候选；
校验字段；
确认 anchor 真的存在于原文；
把脏数据挡在外面。
```

### 11.2 已校验数据的内部规则

```python
def _remove_truncated_anchors(candidates):
    ...
```

这里不应再大量怀疑 `candidate.line_no`、`candidate.anchor_text` 是否存在，因为它接收的是已经通过 `_try_parse_candidate` 的候选。

它负责：

```text
处理截断关系；
不负责重新校验 LLM 输出。
```

### 11.3 API Client 边界

```text
api_client.py 负责 HTTP 请求、状态码错误、JSON 解析错误。
```

上层页面不应到处直接处理 HTTP 细节。

### 11.4 展示边界

```text
evidence_view / evidence_html 模块负责 HTML escape。
```

因为它打开了 unsafe HTML 展示，所以展示层必须负责转义外部文本。

### 11.5 状态边界

```text
state.py 负责 session / 页面状态的初始化、重置和切换。
```

渲染函数不应到处散落状态清理规则。

### 11.6 文本处理边界

```text
text.py 负责句读拆分、缩进、文本展示前处理。
```

它不应该调用 API，也不应该知道模型或数据库。

## 12. 函数 → 模块 → 文件夹 → 子系统的统一规则

每一层都可以问同样的问题。

### 12.1 函数层

```text
这个函数负责什么？
输入是什么？
输出是什么？
它是否接收不可信数据？
如果是，它是否负责校验？
如果不是，它是否可以相信上游契约？
```

### 12.2 模块层

```text
这个模块的稳定职责是什么？
它对外暴露哪些函数？
它内部有哪些私有辅助函数？
外部传入的数据由模块入口清洗，还是调用方保证？
模块内部函数是否可以相信内部契约？
```

### 12.3 文件夹层

```text
这个文件夹代表哪个子领域？
哪些模块属于这个领域？
对外入口是什么？
外部不应该直接依赖哪些内部细节？
```

### 12.4 前后端 / 客户端-服务端层

```text
前端负责展示和交互。
后端负责业务流程和数据契约。
接口响应是双方契约。
前端不能假设后端永远成功。
后端不能相信前端输入永远合法。
错误格式也应尽量稳定。
```

### 12.5 运维 / 环境层

```text
代码负责行为。
环境负责配置。
密钥和环境差异不应硬编码在业务代码里。
配置缺失应在启动或边界调用时明确失败。
```

## 13. 页面文件拆分尺度示例

如果一个页面文件变大，不要按控件碎片拆，而应按稳定页面区域或职责拆。

适合拆：

```text
directory.py：目录、筛选、分页。
poem_view.py：正文展示、阅读模式、聚焦阅读。
tools_panel.py：右侧工具栏、AI 审阅入口、手动查询表单。
evidence.py：证据卡片、审阅结果 HTML。
state.py：状态回调和状态重置。
api_client.py：与后端或外部接口通信。
text.py：文本拆分和显示前整理。
```

不适合过早拆：

```text
button_helpers.py
caption_helpers.py
popover_helpers.py
columns_helpers.py
markdown_helpers.py
```

原则：

> 按“页面区域 / 稳定职责”拆，不按“每个控件 / 每种语法”拆。

## 14. Review 检查清单

审查代码时，按以下问题检查。

### 14.1 抽象是否合适

```text
1. 抽出的函数是否有具体、稳定、领域含义明确的名字？
2. 读者不点进去，能否理解主流程？
3. 函数参数是否自然？
4. 是否存在 4 个以上参数的私有函数？
5. 是否把几行直观代码过度封装了？
6. 是否有 process / handle / do_step 这类空泛函数名？
7. 是否为了函数短而牺牲了阅读连贯性？
```

### 14.2 边界是否清楚

```text
1. 哪些数据是不可信输入？
2. 哪一层负责校验？
3. 数据通过校验后，内部是否仍到处重复防御？
4. .get() / fallback 是否散落过多？
5. try/except 是否包住了真正可能失败的外部操作？
6. 错误处理是中断、降级还是跳过？是否清楚？
```

### 14.3 层级是否混乱

```text
1. 一个函数是否同时混合业务流程、HTTP 细节、展示拼接？
2. 一个模块是否同时承担状态、请求、渲染、业务规则？
3. 一个文件夹是否只是文件堆放，而不是领域边界？
4. 前端是否直接承担了后端业务判断？
5. 后端是否混入了太多展示层格式？
```

### 14.4 是否有 AI 快速开发痕迹

```text
1. 补丁式追加分支。
2. 同名函数导入后又本地定义。
3. 无意义中间变量。
4. 到处兜底。
5. 兼容未来功能的接口提前出现。
6. 函数短但跳转过多。
7. 模块多但职责不稳定。
```

## 16. 给施工 AI 的抽象与边界约束提示词

可以直接复制给施工 AI：

```text
请控制抽象粒度，不要机械地把每几行都抽成函数。

抽函数必须满足至少一个条件：
1. 该逻辑复用 2 次以上；
2. 该逻辑是一个独立业务步骤，能用具体函数名表达；
3. 留在主函数中会打断主流程；
4. 它适合单独测试或以后单独修改。

不要抽函数的情况：
1. 只有 2–5 行，且留在原地更直观；
2. 函数名只能起成 process_data / handle_item / do_step 这类空泛名字；
3. 抽出来需要传 4 个以上参数；
4. 抽出来后读者必须频繁跳转才能理解主流程；
5. 它只是某个局部表达式或临时变量组合。

边界防御要求：
1. 防御式编程集中在不可信边界：用户输入、模型输出、外部 API、数据库、文件、环境变量、前后端通信。
2. 通过边界校验后的内部数据，应尽量被信任，不要在内部流程到处 .get() / fallback / try。
3. 新增任何 try/except 或默认值时，说明它在防什么，以及为什么应该放在这里。
4. 不要为了未来功能提前抽象，不要新增未要求的模块、类或接口。

主函数不要追求极短，而要追求抽象层级一致、主线清楚。
允许在主函数中保留少量有助于理解流程的轻量循环或判断。
```

## 18. 最终目标

这个 Skill 的最终目标不是让代码越来越“架构化”，而是让代码在增长时仍然可理解。

成功标准不是：

```text
函数越短越好；
文件越多越好；
边界越多越好；
防御越全越好。
```

成功标准是：

```text
主线清楚；
职责稳定；
边界明确；
内部信任；
复杂性在该出现的地方出现；
项目负责人能说清楚它为什么这样组织。
```

最重要的一句话：

> 好的工程不是“尽量抽象”和“到处防御”，而是让该负责的层负责，其他层不要越界。
