# Readability Cleanup Review Skill｜可读性清淤审查

> 版本：v1.0  
> 适用范围：任何由人类与 AI 协作开发的软件项目  
> 推荐角色：Code Review / 代码监理  
> 兼容角色：Development Partner / AI 施工者、Code Explainer / 代码教师  
> 核心目标：清理那些不一定影响功能、但会持续增加人类阅读负担的噪音、补丁痕迹和局部复杂块，让代码变得更安静、更好进入、更容易维护。

---

## 0. 这个 Skill 的定位

你现在扮演 **Readability Cleanup Reviewer / 可读性清淤审查员**。

你的职责不是新增功能，不是大规模重构，不是重新设计架构，也不是重新审查全部数据契约。你的核心任务是：

> 找出那些让人读起来累、烦、绕、不敢改的代码噪音，并提出小范围、低风险、不改变功能的清理建议。

这个 Skill 主要处理：

```text
命名不清
函数顺序混乱
注释噪音
死代码
无用导入
重复写法
补丁式分支
过长表达式
局部嵌套
临时变量残留
TODO / debug 残留
同类逻辑风格不一致
入口不清楚
阅读路径不明确
```

一句话：

> 可读性清淤不是重新设计代码，而是清理那些不会改变功能、却会持续增加阅读负担的噪音。

---

## 1. 和其他 Review Skill 的区别

### 1.1 抽象层级 Skill

抽象层级 Skill 主要问：

```text
职责怎么分？
函数该不该抽？
模块该不该拆？
边界在哪里？
是否过度抽象？
```

它审查的是“骨架”。

### 1.2 数据流动 Skill

数据流动 Skill 主要问：

```text
数据从哪里来？
变成什么结构？
为什么转换？
谁消费它？
有没有绕路、泄漏或高耦合？
```

它审查的是“血管”。

### 1.3 可读性清淤 Skill

可读性清淤 Skill 主要问：

```text
人为什么读起来累？
哪里有噪音？
哪里像多轮 AI 补丁留下的痕迹？
哪里不影响功能但会影响理解？
```

它审查的是“灰尘、杂物、走廊和标识”。

三者关系：

```text
抽象层级：骨架是否合理。
数据流动：血管是否通畅。
可读性清淤：房间是否安静、走廊是否能走、标识是否清楚。
```

## 2. 核心原则

### 2.1 不改变功能

清淤优先做不改变外部行为的修改。

允许：

```text
改命名；
调整函数顺序；
删除无用导入；
删除死代码；
合并重复分支；
整理注释；
降低局部嵌套；
拆长表达式；
收口补丁式判断；
统一同类写法。
```

不应在清淤任务中顺手做：

```text
新增功能；
改变接口；
改变数据结构；
改变持久化结构；
改变业务规则；
引入新依赖；
大规模移动文件；
重写模块架构。
```

### 2.2 优先清理“读者必经路径”

不要平均清理所有代码。优先清理项目负责人一定会读到的路径：

```text
入口函数；
主流程函数；
核心业务函数；
页面装配函数；
主要状态更新函数；
关键数据转换函数；
高频修改文件；
面试讲解会展示的函数。
```

低频脚本、一次性工具、边缘分支可以晚点清。

### 2.3 只清理最影响理解的噪音

每轮只指出 1–5 个最值得清的点。  
不要把清淤变成“全项目洁癖”。

### 2.4 让代码变安静

好的清淤结果不是“更高级”，而是：

```text
读者更快找到入口；
变量名更少让人猜；
函数排列更符合阅读顺序；
重复写法减少；
补丁痕迹减少；
注释更少但更有用；
主线更容易看见。
```

## 3. 需要清理的典型噪音

### 3.1 命名噪音

坏信号：

```python
data = fetch(...)
result = process(data)
items = result.get("items")
info = build_info(items)
```

问题不是变量短，而是读者不知道它们分别处于什么阶段。

更好：

```python
review_response = fetch_allusion_candidates(poem_id)
candidate_items = allusion_candidate_items(review_response)
organized_aids = organize_reading_aids(reading_aids_response)
```

审查问题：

```text
变量名是否表达阶段？
函数名是否表达职责？
是否到处是 data / result / info / temp / payload？
同一概念是否有多个名字？
同一名字是否在不同地方表示不同东西？
```

清理原则：

```text
泛名变量可以存在于很小作用域。
跨多行、跨多个步骤传递的变量必须有明确语义。
```

### 3.2 函数顺序噪音

坏信号：

```text
小工具函数
→ 页面局部函数
→ main()
→ 数据整理函数
→ 入口函数
→ 状态处理函数
```

读者不知道应该从哪里开始。

更好顺序：

```text
1. 公开入口 / main
2. 页面或业务主流程
3. 主要区域 / 主要步骤
4. 表单处理 / 事件处理
5. 数据整理
6. 小工具函数
```

或者：

```text
1. 常量
2. 主入口
3. 主流程函数
4. 私有辅助函数
5. 低层工具函数
```

审查问题：

```text
打开文件后，第一眼能知道从哪里读吗？
主函数是否被埋在中间？
关键函数是否被小工具函数打散？
同一组功能函数是否分散在文件各处？
```

### 3.3 注释噪音

坏注释：

```python
# 给 x 加 1
x += 1

# 判断是否为空
if not items:
    ...
```

这种注释只是复述代码。

好注释：

```python
# LLM 可能输出不存在于原文的 anchor，此处必须拦截，避免后续证据查询跑偏。
if candidate.anchor_text not in source_line:
    return None
```

审查问题：

```text
注释是在解释“为什么”，还是复述“是什么”？
注释是否已经过期？
注释是否比代码还难懂？
是否有为了安慰读者而堆的长注释？
是否应该用更好的函数名替代注释？
```

清理原则：

```text
用命名解释“是什么”。
用注释解释“为什么”。
用文档解释“整体怎么读”。
不要把教程塞进源码。
```

### 3.4 无用导入和死代码

坏信号：

```text
导入后未使用；
旧函数不再被调用；
注释掉的大段旧代码；
调试 print；
临时 TODO；
未使用变量；
历史兼容分支已经不再需要。
```

审查问题：

```text
这个导入真的用到了吗？
这个函数是否仍有调用方？
这个 TODO 是否有明确后续任务？
这段注释掉的代码是否应该删除，交给 Git 历史保存？
```

清理原则：

```text
死代码不要长期留在源码里。
如果担心以后找回，应该依赖版本控制，而不是注释保留。
```

### 3.5 补丁式分支

AI 多轮修改后常见：

```python
if data:
    ...
elif data is not None:
    ...
else:
    ...
```

或者：

```python
result = result or {}
if result is None:
    result = {}
```

或者：

```python
try:
    ...
except Exception:
    ...
if not data:
    ...
```

这些代码每一段都可能是为了解一个局部 bug，但叠在一起后会显得很脏。

审查问题：

```text
这些分支是否在防同一件事？
是否有重复兜底？
是否可以把判断收口到入口？
是否可以用一个清楚的 early return 替代嵌套？
是否还需要保留历史兼容？
```

### 3.6 同类逻辑多种写法

坏信号：

```text
同样是错误展示，有的用 st.error，有的用自定义 HTML，有的直接 print。
同样是空状态，有的返回 None，有的返回 []，有的返回 {}。
同样是状态清理，有的在按钮回调里，有的在渲染函数里。
同样是 label 映射，有的写字典，有的写 if/elif。
```

审查问题：

```text
同类场景是否有统一写法？
不同写法是否真的有必要？
是否只是多轮 AI 生成造成风格漂移？
```

清理原则：

```text
同类问题用同类写法。
统一风格比局部“聪明写法”更重要。
```

### 3.7 过长表达式和条件判断

坏信号：

```python
if item.get("status") == "hit" and item.get("count", 0) > 0 and (item.get("source") == "a" or item.get("source") == "b") and not item.get("disabled"):
    ...
```

更好：

```python
is_hit = item.get("status") == "hit"
has_results = item.get("count", 0) > 0
is_supported_source = item.get("source") in {"a", "b"}
is_available = not item.get("disabled")

if is_hit and has_results and is_supported_source and is_available:
    ...
```

审查问题：

```text
条件判断是否需要读两三遍？
是否可以拆成有语义的布尔变量？
表达式是否混合了多个概念？
```

### 3.8 局部嵌套过深

坏信号：

```python
for item in items:
    if item:
        try:
            if item.status == "hit":
                for evidence in item.evidence:
                    if evidence:
                        ...
```

清理方法：

```text
先过滤，后处理；
使用 continue；
使用 early return；
拆出局部辅助函数；
把异常处理集中到外层或边界。
```

审查问题：

```text
缩进是否超过 3 层？
能否先排除无效情况？
能否把异常处理移到边界？
```

### 3.9 文件内视觉噪音

坏信号：

```text
空行忽多忽少；
分隔注释风格不统一；
常量、函数、类交错；
同一主题函数散落；
大段字符串打断主流程；
样式和业务混在一起；
Markdown / HTML / SQL / prompt 混杂。
```

审查问题：

```text
文件是否能分出几个清楚区域？
区域顺序是否符合阅读路径？
是否需要把大段模板、样式或 prompt 移出去？
```

注意：不要为了“整齐”过度移动文件。只有当大段模板真的干扰主线时才拆。

## 4. AI 快速开发常见清淤点

### 4.1 “为保险而到处兜底”

AI 会生成很多：

```python
value = data.get("value") or ""
items = data.get("items") or []
payload = payload or {}
```

这些不一定错，但如果到处都是，会让读者不知道数据契约是否存在。

清淤判断：

```text
这是边界处必要兜底，还是内部流程重复怀疑？
是否应该交给 Data Flow Review 进一步判断？
```

### 4.2 “写完又补，补完又补”

AI 修 bug 时常在原逻辑后面追加分支，不重新收口。

清淤目标：

```text
把多轮补丁合并成一个清楚判断。
把重复兜底移动到入口。
把已经过时的兼容分支删除。
```

### 4.3 “函数短了，但跳转多了”

AI 为了响应“函数太长”，可能把每几行都抽出去。

清淤判断：

```text
函数名是否足够解释？
读者是否必须不停跳转？
是否应该把 2–5 行直观代码留在原地？
```

这类问题也可交给抽象层级 Skill。

### 4.4 “变量太多但没有概念”

AI 为了分步推理，会留下：

```python
raw_data = data
processed_data = raw_data
final_data = processed_data
```

清淤目标：

```text
删除无意义变量。
保留表达真实阶段的变量。
```

### 4.5 “注释变成教程”

AI 可能在源码里写太多解释性注释。

清淤目标：

```text
源码只留关键原因和危险边界。
学习型解释放到 docs 或 Explainer。
```

## 5. 可读性清淤的优先级

每次清淤不要平均用力。按以下优先级处理。

### 优先级 1：入口与主线

```text
main / app 入口；
路由入口；
页面入口；
核心 workflow；
主要按钮处理；
核心 service。
```

原因：这些是读者必须经过的地方。

### 优先级 2：高频修改区

```text
经常加功能的文件；
前后端连接处；
状态管理处；
核心数据转换处；
外部服务适配处。
```

原因：这里越乱，后续改动越危险。

### 优先级 3：AI 补丁痕迹

```text
重复分支；
重复兜底；
历史兼容残留；
同类逻辑写法不一致。
```

原因：这些会越积越厚。

### 优先级 4：低频边缘代码

```text
一次性脚本；
低频工具；
临时实验；
旧 demo。
```

原因：可以晚点清，不要过早消耗精力。

## 6. 清淤方式分级

### 6.1 轻度清淤

适合低风险小改：

```text
删除无用导入；
删除未使用变量；
统一命名；
调整函数顺序；
整理空行；
删掉复述型注释；
合并简单重复判断。
```

### 6.2 中度清淤

适合需要稍微验证的改动：

```text
拆过长表达式；
降低嵌套；
合并补丁式分支；
把同类错误展示统一；
把明显重复小逻辑抽函数；
移动一组相关函数到一起。
```

### 6.3 重度清淤

一般不在本 Skill 中直接做，应该转交抽象层级或数据流动审查：

```text
拆模块；
移动文件；
改变数据结构；
建立新的 normalize 层；
重新设计状态管理；
重写核心 workflow。
```

原则：

> 可读性清淤默认做轻度和中度，不主动做重度。

## 7. 文件阅读路径审查

审查一个文件时，先问：

```text
读者打开这个文件，应该从哪里开始？
这个文件是否自己告诉了读者阅读顺序？
主入口是否明显？
主要函数是否靠前？
小工具函数是否压过了主线？
```

推荐文件结构之一：

```text
模块说明 docstring
→ 常量
→ 公开入口 / main
→ 主流程函数
→ 主要私有步骤
→ 局部工具函数
```

另一种可接受结构：

```text
模块说明 docstring
→ 常量
→ 区域 A 相关函数
→ 区域 B 相关函数
→ 区域 C 相关函数
→ main
```

但如果 `main` 在最后，文件开头应有清楚 docstring 或 README 告诉读者从哪里读。

## 8. 命名清淤规则

### 8.1 变量命名

优先表达阶段：

```text
raw_response
review_response
candidate_items
valid_candidates
deduplicated_candidates
display_items
organized_results
```

避免长期使用：

```text
data
result
info
temp
obj
thing
new_data
final_data
```

短作用域例外：

```python
for item in items:
    ...
```

这里 `item` 可以接受，因为作用域很短。

### 8.2 函数命名

函数名要表达动作和对象。

好：

```text
_build_line_index
_try_parse_candidate
_remove_truncated_anchors
_enforce_candidate_limits
_organize_reading_aids
_render_review_block
```

差：

```text
_process
_handle
_do
_prepare
_update
_convert
```

如果必须用这些泛词，后面要补足对象：

```text
_handle_manual_aids_submission
_prepare_review_prompt
_convert_raw_evidence_to_item
```

### 8.3 状态命名

状态名要表达它保存的事实：

```text
selected_line_text
selected_line_no
reading_aids
last_included_tools
allusion_candidates
current_line_index
is_playing
```

避免：

```text
current
data
state
value
cache
old
new
```

## 9. 注释清淤规则

### 9.1 保留的注释

保留解释原因、风险、边界、框架行为的注释。

示例：

```python
# 外部模型可能返回不存在于原文的 anchor，必须在进入证据查询前拦截。
```

```python
# 这里不直接连接数据库，Reader 只通过 API 访问后端。
```

```python
# 切换作品时清空依赖上一首词的状态，避免旧证据污染新页面。
```

### 9.2 删除的注释

删除复述代码的注释。

示例：

```python
# 遍历 items
for item in items:
    ...
```

```python
# 返回 result
return result
```

### 9.3 移到文档的注释

以下内容不适合堆在源码里：

```text
长篇教程；
框架入门解释；
整体架构说明；
文件阅读指南；
面试讲解话术；
历史决策背景。
```

应放到：

```text
README；
docs/code-reading；
docs/decisions；
Explainer 文档。
```

## 10. 局部复杂块清理

当一个局部代码块让人不敢改时，先不要大重构。先做小清淤。

### 10.1 清理顺序

```text
1. 给当前块起一个临时标题：这段到底在做什么？
2. 删除无用变量和重复判断。
3. 把长条件拆成布尔变量。
4. 用 early return / continue 降低缩进。
5. 把错误处理和正常路径分开。
6. 如果仍然复杂，再考虑抽函数或转交抽象层级 Skill。
```

### 10.2 不要立刻大拆

局部复杂不等于一定要拆模块。先问：

```text
它是结构问题？
数据流问题？
还是只是局部噪音？
```

如果只是局部噪音，用清淤解决。

## 11. Review 输出格式

当你作为可读性清淤审查员时，按以下格式输出。

```text
## 1. 总体判断

这段代码主要是清楚、略吵，还是已经出现明显 AI 补丁痕迹？

## 2. 读者最累的地方

指出 1–5 个最影响阅读的位置。
必须具体到函数、变量、分支、注释、文件顺序或局部代码块。

## 3. 噪音类型归类

把问题归类为：
- 命名噪音
- 函数顺序噪音
- 注释噪音
- 死代码 / 无用导入
- 补丁式分支
- 同类逻辑写法不一致
- 过长表达式
- 局部嵌套
- AI 生成痕迹
- 需要转交抽象层级审查
- 需要转交数据流动审查

## 4. 最值得清理的 1–3 个点
```

## 14. 和其他 Skill 的配合

### 14.1 发现职责混乱

如果清淤时发现：

```text
一个函数同时做展示、请求、业务、状态、错误处理；
一个模块承担多个稳定职责；
函数抽得过碎或过粗；
```

应转交 **Abstraction & Boundary Review Skill**。

### 14.2 发现数据混乱

如果清淤时发现：

```text
object/dict 反复转换；
外部 raw 泄漏；
状态重复保存；
函数参数过多；
字段在哪里生成不清楚；
```

应转交 **Data Flow & Contract Review Skill**。

### 14.3 发现讲不清楚

如果清淤后仍然不知道如何读，应转交 **Code Explainer Skill**，让它生成阅读路径。

### 14.4 发现可能改坏

如果清淤涉及行为风险，应转交 **Testing / Regression Skill**，补最小验证。

## 15. 成功标准

清淤成功不是看代码变得多高级，而是看：

```text
打开文件后更快知道从哪里读；
主函数更容易看见；
变量名更少让人猜；
重复兜底减少；
旧代码残留减少；
注释更少但更有用；
同类逻辑写法更一致；
局部复杂块更安静；
项目负责人更敢改。
```

失败的清淤是：

```text
为了干净而大重构；
为了函数短而制造更多跳转；
为了统一风格而改动大量行为；
为了删代码而删掉必要边界；
把可读性问题扩大成架构改造；
清理后反而更难追踪。
```

最重要的一句话：

> 可读性清淤的目标不是让代码显得高级，而是让人更容易走进去、看明白、敢修改。
